### ทรัพยากรรับไหวไหม (เว็บ SaleForce + เว็บโชว์รูม + แอปมือถือ + n8n)
- **เว็บโชว์รูม (:8080) กับ API ของแอปมือถืออยู่บนเครื่อง SaleForce อยู่แล้ว** — ตัวเลขข้างบนรวมไว้แล้ว
  (แอปมือถือไม่มีเซิร์ฟเวอร์ของตัวเอง เรียก API ของ SaleForce) → **ของใหม่ที่เพิ่มจริงคือ n8n อย่างเดียว**
- **CPU / ดิสก์ เหลือเฟือ · ตัวที่ตึงคือแรม** — ช่วงพีคเหลือ ~1.5–2 GB · แรมของ SaleForce ไต่ขึ้นทั้งวัน
  (2.4 → 4.0 GB วันที่ 12 ต.ค.) แล้วลดลงหลังรีสตาร์ต = worker ของ gunicorn ค่อยๆ บวม
- **กันไว้แล้วใน `docker-compose.yml`**: n8n ทั้งชุดมีเพดานแรม (n8n 3 GB · ตัวรันโค้ด 1.5 GB · ฐานข้อมูล 1 GB)
  → ถ้า n8n แรมพุ่ง ตัวที่ล้มคือ n8n เอง (แล้วฟื้นเอง) ไม่ใช่เว็บ SaleForce · log ของ docker หมุนที่ 10 MB × 3
- **แนะนำเพิ่มก่อนย้าย** (ทำครั้งเดียว ~1 นาที · `check` บอกว่ามี swap หรือยัง):
  ```bash
  fallocate -l 4G /swapfile && chmod 600 /swapfile && mkswap /swapfile && swapon /swapfile && echo '/swapfile none swap sw 0 0' >> /etc/fstab
  ```
  swap = ที่พักชั่วคราวตอนแรมพุ่งแป๊บเดียว (เช่นแคปรูปรายงานพร้อมกับ n8n รัน AI) กันระบบไล่ฆ่าโปรแกรม
- **แนะนำ (ไม่บังคับ)**: ให้ gunicorn เปลี่ยน worker ใหม่เป็นระยะ แก้แรมบวมระหว่างวัน — เติม
  `--max-requests 2000 --max-requests-jitter 200` ใน `/etc/systemd/system/oxlet.service` แล้ว
  `systemctl daemon-reload && systemctl restart oxlet`

- **ชื่อ `n8n.srv1793506.hstgr.cloud` ชี้มาเครื่อง SaleForce อยู่แล้ว** (DNS ของ Hostinger) ไม่ต้องตั้งอะไร
- เครื่องเดิมใช้ **Traefik** คุมพอร์ต 80/443 — ย้ายมาแล้วใช้ **nginx ของ SaleForce** แทน (เพิ่มไฟล์ใหม่ 1 ไฟล์ ไม่แตะของเดิม)
- ฐานข้อมูลของ n8n เป็น **Postgres แยกใน docker** — ไม่ปนกับฐานข้อมูล SaleForce · ไม่เปิดพอร์ตออกนอก
- ย้าย **ทั้งฐานข้อมูล** = workflow ทุกตัว (63 ตัว) · credential ทุกตัว · บัญชีผู้ใช้ · สถานะเปิด/ปิด ตามมาครบ
  (ใช้กุญแจถอดรหัสตัวเดิม — สคริปต์คัดไปให้เองโดยไม่โชว์บนจอ)
- **เวอร์ชันเดิมเป๊ะ** (2.22.5) · **timezone เดิม** (Europe/Berlin) → เวลา schedule ทุกตัวไม่เลื่อน
- n8n ต่อฐานข้อมูล SaleForce ผ่านอุโมงค์ SSH ไปที่ IP เครื่อง SaleForce → **ย้ายมาแล้วยังใช้ได้เหมือนเดิม**
- **สิ่งเดียวที่คุณต้องทำเอง: แก้ Webhook URL** ในบริการที่ยิงเข้า n8n (LINE Developers · Fireflies ฯลฯ) —
  เปลี่ยนแค่ชื่อเครื่อง `srv1102218` → `srv1793506` · path ไม่เปลี่ยน · สคริปต์พิมพ์รายการให้

## ขั้นตอน

### 1) ดูก่อน — ไม่แก้อะไรทั้ง 2 เครื่อง (ทำเมื่อไหร่ก็ได้)
```bash
bash /opt/oxlet/deploy/n8n_move/move.sh check
```
ส่งผลบนจอให้ Claude ดู — โดยเฉพาะ **ขนาดฐานข้อมูล n8n / โฟลเดอร์ข้อมูล** (ถ้าใหญ่หลาย GB ต้องเคลียร์ก่อนย้าย)

### 2) เตรียมเครื่องใหม่ — n8n เดิมยังทำงานปกติ ไม่มีช่วงหยุด (ทำกลางวันได้)
```bash
bash /opt/oxlet/deploy/n8n_move/move.sh prepare
```
ลง Docker · โหลด n8n เวอร์ชันเดียวกับเครื่องเดิม · เปิดฐานข้อมูลเปล่า · ตั้ง nginx + ใบรับรอง https
**ยังไม่เปิด n8n** (กันทำงานซ้อนกับเครื่องเดิม)

### 3) ย้ายจริง — n8n หยุด ~10–20 นาที (ทำตอนดึก ~22:30 · **ห้ามช่วง 06:00–10:00** = ช่วงเช็คชื่อ)
```bash
bash /opt/oxlet/deploy/n8n_move/move.sh cutover
```
หยุด n8n เครื่องเดิม (ไม่ลบ) → สำรองฐานข้อมูล + ไฟล์ → ดึงมาเครื่องนี้ → ตรวจว่าครบ → เปิด n8n ที่นี่
→ พิมพ์ **รายการ Webhook URL ใหม่** · ระหว่างย้าย ข้อความ LINE ที่วิ่งเข้า n8n จะไม่ถูกประมวลผล

### 4) แก้ Webhook URL (ทำทันทีหลังขั้นที่ 3)
- **LINE Developers** → แต่ละ channel ที่ Webhook URL ขึ้นต้นด้วย `https://n8n.srv1102218.hstgr.cloud/`
  → Messaging API → Webhook URL → เปลี่ยนเป็น `https://n8n.srv1793506.hstgr.cloud/` + path เดิม → **Verify**
- **Fireflies** (webhook ของ WF0 ทะเบียนประชุม) · บริการอื่นที่ยิงเข้า n8n
- ดูรายการซ้ำได้ตลอด: `bash /opt/oxlet/deploy/n8n_move/move.sh webhooks`

### 5) workflow ที่ฝังชื่อเครื่องเดิมไว้ข้างใน (ถ้าขั้นที่ 3 บอกว่ามี)
```bash
bash /opt/oxlet/deploy/n8n_move/move.sh fixurls
```
สำรองฐานข้อมูลก่อน แล้วแทน `n8n.srv1102218.hstgr.cloud` → `n8n.srv1793506.hstgr.cloud` ในตัว workflow

### 6) ตรวจว่าใช้ได้
- เปิด https://n8n.srv1793506.hstgr.cloud → login ด้วย **อีเมล/รหัสผ่านเดิม**
- เมนู Executions → มีรอบใหม่ไหลเข้ามา (schedule ทำงาน)
- พิมพ์ในกลุ่ม LINE → workflow ที่รับ LINE ทำงาน
- SaleForce → ตั้งค่า → สถานะระบบ → "cron ทำงานล่าสุด" ต้องเป็นนาทีล่าสุด
- เช้าวันถัดไป: รูปเช็คชื่อถูกบันทึก (เมนู เช็คชื่อเข้างาน)

## ย้อนกลับ (ใช้ได้จนถึง 3 พ.ย.)

